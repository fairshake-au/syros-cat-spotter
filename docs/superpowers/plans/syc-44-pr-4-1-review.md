## Detail

**1. Unchecked-draft queries have no test.** I deleted `isWelfare` from the unchecked draft list (`welfareQueue.ts:363`) and from the unchecked draft count (`:372`): all 36 tests across T4-0..T4-8 and `internalMail` still pass. The checked variants (`:342`, `:351`) do go red. Why it matters: a content row that is a draft with `token_checked = false` would show in the "Unchecked" drafts list and count. Content drafts probably never exist (the issue route inserts sent rows), which is why this is Minor. Fix: in `team.kind.test.ts` add `seedReport({ kind: "content", reason: "other", isDraft: true, tokenChecked: false })` next to `:171`; the byte-for-byte snapshot then covers both.

**2. Unchecked-waiting count has no test.** Removing `r.kind = 'welfare'` at `outbox.ts:221` passes every test. Fix: in `internalMail.test.ts` (T4-5), seed an open content row with `tokenChecked: false` and no outbox row, enqueue the waiting email, and assert `waiting` ignores it. Do it before Slice 5 lands.

**3. Two untested guards.** (a) `reports.ts:351` is only reached when the upsert returns no row (a sent report already exists); an unfiltered lookup could return the content row's public id to a welfare resend. The earlier `sentReport` pre-check hides it in all but a race. A test needs two concurrent submits, so a code-comment may be the honest answer. (b) The `alertEmail.ts:117` throw is defence in depth behind the outbox `wrong_kind` check (which is tested and goes red when removed). A one-line unit test in `alertEmail.test.ts` (row with `lat: null` throws) closes it.

**4. `null` answers.** The PR body already admits this. Confirmed not a crash: `res.json(null)` sends `200 null`; the form path redirects to `/api/team` where the row is not listed. Unreachable until a content row exists. Fix with Slice 7 (the Issues section gets its own answer shape), or make these three routes return 404 for a `kind = 'content'` id in the interim. Related and fine: `GET /team/cats?tie=<id>` with a content id gets `report: null`, which `catPages.ts:183` already handles ("can't find that report").

**5. Old key vs new target.** On the migrated schema I ran: welfare + old-key upsert (works), welfare + new-key upsert (works), content row with the same device and ref (blocked by the old key, as the migration test says). The converse, a welfare insert after a content row exists, is a 23505 on the old key that the upsert does not catch. Fix: no code change; record in Linear/PR 5.1 gate that 4.2 is merged and migrated first (the plan already says "Slice 5 needs 4.2"; make it a checklist line on 5.1).

**6. T4-6 index drop.** Risk is low and confined to the throwaway database (`src/test/globalSetup.ts` creates it; it is dropped at the end of the run). Suggested hardening, optional: run the drop in a short transaction with `SET LOCAL lock_timeout = '2s'` and skip T4-6 loudly if it cannot get the lock, or move T4-6 into the 4.2 PR where the old key is genuinely gone and delete the workaround.

**7. Rollback and hidden photos.** Note for Slice 5, not for this PR.

- **Sweep of every reader/writer** (grep for `welfareReportsTable`, `welfare_reports`, `WelfareReport`, `report_state_events`, `reportStateEventsTable`, `mail_outbox.report_id`, `welfare_alert`, `welfare_outcome`, `is_draft`, `getQueueReport|listWelfareQueue|moveReportState|writeTeamNote|tieReportToCat` across `artifacts`, `lib`, `scripts`, `infra`). No push roundup, export, team page, cat page or guardian code reads the table. `teamCats.ts`/`catPages.ts` only call `getQueueReport`. `routes/teamReports.ts` photo route reads `welfare_report_photos` by its own public id, which a content row never has. `infra/mail-drain-cron` only calls an HTTP endpoint.
- **Every query in every allowlisted file has its rule:** `welfareQueue.ts` (lists, closed list + count, drafts + counts, unchecked list + count, `getQueueReport` all carry `isWelfare`; `mailHealth` counts both alert purposes; `mailStatesFor` filters purpose and report ids), `welfareActions.ts` (outcome only for welfare), `welfareTie.ts` (`not_welfare` before any write; route answers 409), `outbox.ts` (`wrong_kind`, unchecked count), `reports.ts` (both upserts write `kind` and name the new key; `sentReport`, existing lookup and photo PUT filter welfare), `severPerson.ts` (no filter, on purpose).
- **Migration 0023 enforces what it claims.** Probed on a fresh migrated database: content row with `photo_state` attached, with `severity` urgent, with `is_litter` true, with reason null, `kind` flipped to welfare while reason set, welfare row with `lat` null, welfare row flipped to content while keeping `severity`: all refused by the named checks. Welfare rows keep `lat`/`lng` required (`welfare_reports_position_ck`). Existing rows already satisfy every new check (all had a position, kind `welfare`, no reason). The reason-to-kind link is both ways. Photo reasons require `photo_id`; `photo_id` is a real foreign key.
- **Live traffic between migrate and publish.** Old code's upsert `on conflict (reporter_device, client_ref)` still resolves to the surviving old unique index and updates the row (probed: returned the same id). New code's `on conflict (reporter_device, kind, client_ref)` resolves to the new index (probed). Old inserts omit `kind` and default to `welfare`; old reads see non-null lat/lng for every existing row. The reverse (new code on an unmigrated database) would fail every report, which the plan covers by "migrate, then publish; roll the app back first, then the database".
- **Rollback.** Via the real CLI on a database with a welfare row and a content row: `rolled back: 0023_issue_reports`, the content row is deleted, the welfare row stays, `lat`/`lng` are NOT NULL again, then `up` re-applies cleanly. The warning is the first line of the block and is tested. Foreign keys that point at a report cascade or set null (tested for `mail_outbox`).
- **Test isolation of T4-6.** It touches only the per-run throwaway database; its cleanup is scoped to its own device prefix, so the recreate cannot hit a duplicate; no other api-server test names the old index; `pool.end()` is its own.
- **Mutation probes from the PR body, re-run by me, all go red:** drop the `kind` filter in `reportsQuery` (T4-1 x2, T4-2 x2 red); drop the outcome guard (T4-3 red); let the tie accept content (T4-4, 2 red); photo PUT without the kind (T4-8 red); `sentReport` without the kind (T4-6, 5 red); `mailHealth` counting only `welfare_alert` (T4-2, 3 red); outbox without the kind check (T4-5 red); closed count, checked-draft list/count, unchecked count each red on the T4-1 snapshot.
