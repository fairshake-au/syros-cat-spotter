# Adversarial review: SYC-705 map labels in your language (v3, commit f1698d19, MapLibre on every map)

Read-only review. Spec: docs/specs/map-labels-in-your-language.md. Prototype: docs/specs/source/map-labels-style-prototype.html. Dashboard picture-design findings dropped per coordinator.
Line numbers refer to the worktree files as of f1698d19.

## BLOCKERS

B1. cellShape.ts depends on the file the spec deletes.
- artifacts/cat-spotter/lib/cellShape.ts:9 imports MIN_ZOOM, fromWorld, toWorld from ./mapTiles. Spec §5 deletes lib/mapTiles.ts; §4 says cellShape "keeps its geometry and drops react-native-maps types". fitRegion (cellShape.ts ~l.130-175), cellBoxPixels and FIT_MAX_ZOOM all use that Mercator maths. AppMap.web.tsx also imports clampZoom, latLngAtOffset, visibleTiles from it.
- Fix: say the Mercator helpers (toWorld/fromWorld/MIN_ZOOM) move into cellShape or a new lib/mercator.ts; delete only the picture-URL and visibleTiles parts. List mapTiles.test.ts and the cellShape tests as rewritten.

B2. Zoom units differ (MapLibre 512 px vs slippy 256 px); the spec ignores it.
- fitRegion returns a "whole tile zoom, as the web map uses" plus latitudeDelta (cellShape.ts ~l.100); zoomForDelta in AppMap.web.tsx:23 uses log2(360/Δ)-1; web MIN/MAX_ZOOM 12/19 (mapTiles.ts:10-11). MapLibre zoom = slippy zoom - 1. Every fitKey fit, the initial region (cats.tsx initialRegion deltas), LocationPicker 0.004 delta, and "the map zoom limits" (Not changing, spec l.~236) will be off by one level unless converted once, centrally.
- Fix: add a "zoom convention" bullet: keep slippy numbers in our code, convert at the MapLibre boundary; add tests comparing FIT results before/after.

B3. Road (and every) label in the Protomaps style becomes two lines once name:en exists, contradicting the spec's table.
- Spec l.49-51 says English readers get "Ermoupoli" with Greek underneath for towns and "Odos Ermou" for everything else (implying one line).
- Evidence: protomaps/basemaps styles/src/base_layers.ts:1452 (roads_labels_minor) uses get_multiline_name(lang…); styles/src/language.ts get_multiline_name (lines ~101-148): when `name` is Greek (not target script) it renders coalesce(name:en…) then "\n" then the local name. So with Decision B filling name:en on 1,000+ streets, every street, shop and church label becomes "Odos Ermou / Οδός Ερμού", along a line at z15+. That doubles label length, hurts fit along streets, and is not what Samuel approved (the prototype only showed this on places because 99% of streets had no name:en; prototype lang is passed to basemaps.layers, so the effect was never visible on streets).
- Fix: decide in the spec. Recommended: for lang=en override text-field on roads/pois/water labels with a single-line ["coalesce",["get","name:en"],["get","name"]] and keep the two-line form only for places (towns/villages). Add a before/after picture of a street and a shop to the approval images. Greek mode is fine (target script, one line).

B4. Native renderer is unproven for this style; Step 1 as written would not catch it.
- The prototype ran only in maplibre-gl-js (prototype html l.4-6). Native (MapLibre Native Android 13.6.1 / iOS 6.31.0 per maplibre-react-native v11.4.0 release notes) differs on expressions: Protomaps' labels use ["is-supported-script"], ["format"] with per-section text-font/font-scale/text-color, "\n" sections, and the adjusted layers add ▲ and † glyphs from "Noto Sans Regular". Step 1 (spec l.~198) only requires "Greek and English labels". Unchecked whether each expression renders on both native platforms.
- Fix: Step 1's test must load the actual adjusted style (all label layers, two-line names, ▲ †, italic beach names, the cell fill/outline layers, text-halo) on a real iPhone and Android, airplane mode, and screenshot against the prototype.

B5. Local-file PMTiles on native: plausible but unproven, and the stated fallback does not work as written.
- Evidence for: maplibre-react-native issue #728 (maintainer repro uses `pmtiles://${localUri}` where localUri is file://...); #618/#625 (iOS NSURL PMTiles, fixed). So the URL must be `pmtiles://file:///…` (relative paths unsupported on Native; MapLibre Native Android PMTiles doc, maplibre.org/maplibre-native/android/examples/data/PMTiles: Android >= 11.7.0, "PMTiles sources do not support offline pack downloads or caching").
- Evidence against the spec's fallback (§4 l.~148, "MapLibre's own offline storage, filled from the same data"): per the same Android doc, PMTiles sources don't support offline packs. The fallback must be a z/x/y vector-tile endpoint (the Worker) feeding OfflineManager.createPack, which is a bigger build (and its tile-count/size limits are unchecked).
- #647: a PMTiles URL containing escaped characters crashes the app (closed for missing repro, reporter saw SIGSEGV). Our file path under iOS documentDirectory has no escapes, but font stacks with spaces ("Noto Sans Regular") are percent-encoded in glyph URLs; whether native decodes %20 for file:// glyph paths is unchecked.
- Fix: state the exact URL form; say the fallback is "serve z/x/y tiles from a Worker and use OfflineManager", cost it, and make Step 1 test: local pmtiles://file://, local glyphs/sprites file://, sprite/glyph path with spaces, on both OSes, plus first launch after an app update (iOS container path can change, see S4).

## SHOULD-FIX

S1. Library facts the spec should state (verified): @maplibre/maplibre-react-native is at v11.5.0 (4 Oct 2026). package/package.json peerDeps: expo >=54 (optional), react >=19.1.0, react-native >=0.80. Repo has expo ~54.0.27, react 19.1.0 (pnpm-workspace.yaml:59), RN 0.81.5, newArch true: compatible. Docs (docs/content/setup/expo.md): needs the config plugin in app.json ("plugins": ["@maplibre/maplibre-react-native"]; it adds the MLRN post_install hook; without it iOS fails to find MapLibre headers, issue #1623), "can't be used with Expo Go". Current repo: no expo-dev-client in cat-spotter/package.json although eas.json has a developmentClient profile; and server/serve.js/scripts/build.js still exist for Expo Go bundles (serve-web.js header). Fix: spec §4 should say app.json gains the plugin, Expo Go stops working for map screens, and Step 1 builds via the "preview" EAS profile or adds expo-dev-client. Android/iOS exact MapLibre Native versions (13.6.1 / 6.31.0 in v11.4.0) are release-note facts; they change per release, so pin the library version.

S2. Web: maplibre-react-native has no web support (issue #1346 closed pointing at #501). The spec does keep the separate .web.tsx files (good, §5). State it plainly as the reason, and note two code paths to test, and that AppMap.web has a bottom "strip" of cat chips and zoom buttons the new web map must keep (AppMap.web.tsx:180-250) and that native passes markers=[] (cats.tsx ~l.325), so spec wording "cat markers" (l.58, l.~143) is wrong for native: native draws cells and "N cats" labels only.

S3. Performance/gestures not specified. Native cells = GeoJSON source + FillLayer/LineLayer (not RN Polygon children); tapping a cell needs map-level press + feature query; the "N cats" label should be a SymbolLayer text (library docs/guides/annotations.md: ViewAnnotation/Marker children are views: iOS interactive, Android static; no clustering; "always on top"). Pitch (two-finger tilt) and rotation are on by default: spec mentions rotation only (Risks) but not pitch; disable pitch. showsUserLocation (AppMap, LocationPicker) needs MapLibre's UserLocation component and an expo-location permission flow; spec silent. LocationPicker's tap-to-centre (animateCamera) and onRegionChangeComplete must be rebuilt (LocationPicker.tsx:50-57).

S4. Offline storage and update details missing.
- Where: spec says "app's own storage". Say documentDirectory (as offlineTiles.ts:22 does), not the cache directory (iOS may purge caches); note documentDirectory is included in iCloud backup, so either exclude it or accept a few MB.
- Never persist absolute file URLs in a stored style: the iOS container path can change across updates/restores. Build the style object with the current path at each launch.
- Atomic swap: download to a temp name, check byte length and a hash from manifest.json, open the PMTiles header (magic "PMTiles", version 3), then rename to a versioned name (syros-v{N}.pmtiles). Never overwrite the file MapLibre has open; reload the style on the new name, then delete the old file. Resume/partial download behaviour is not described (the old code left partial files and retried: offlineTiles.ts:131-135).
- Glyphs/sprites on native: file:// should work (mbgl local file source handles file:// and asset://) but is unchecked; the fonts folder size must be bounded by shipping only the needed ranges (Basic Latin, Latin-1, Latin Extended, Greek 0370-03FF, Greek Extended 1F00-1FFF, General Punctuation 2000-206F for †, Geometric Shapes 25A0-25FF for ▲) for 3 stacks (Regular, Medium?, Italic), not whole Noto fonts. Say which stacks the adjusted style uses; "a few megabytes" is unverified (mark it).
- First launch: spec l.~92 says before the download finishes "the map is blank. That's the same as today." It is not: today, online, react-native-maps draws OSM pictures immediately (OsmTiles.tsx uses the online template until ready). Fix: while the local file is missing and the phone is online, read pmtiles://https://tiles.catspotters.com/... directly (needs the same CORS/range setup, iOS NSURL issue #618 fixed), and switch to the local file when complete. Otherwise first-run spotters on the Spot tab see a blank map for the length of the download.
- Unmentioned importers: app/_layout.tsx:35,57 (OfflineTilesLoader / ensureOfflineTiles) and app/(tabs)/spot.tsx:59,335,1568-1573 (useOfflineTiles progress text, i18n key mapDownloading in en/el/fr, lib/i18n.ts:222,1081,1910), plus lib/__tests__/noStrayApiCallers.test.ts:15 whitelisting lib/offlineTiles.ts for network access. Add all to §4.

S5. Language switch "without reloading" (spec l.~149) is not free on native: changing the mapStyle prop re-parses the whole style (flash). Prototype does a full setStyle (html l.~63). Fix: per-layer text-field updates (setLayoutProperty on web; layer props on native) and test it.

S6. Website bundle/lazy loading unverified. Expo web export is Metro; existing dynamic import() in the repo is only for native-only modules (lib/nativeReminder.ts:14, context/DeviceContext.tsx:118), none proves web chunk splitting. "Roughly 250 KB compressed" is an estimate stated as fact: maplibre-gl 5.x is about 0.8-1 MB minified (roughly 250-300 KB gzip) plus CSS and the worker; unchecked. Also scripts/precompress-web.js and serve-web.js must serve the new chunk and CSS (SYC-133). Fix: mark estimate, add a Step 4 check: `expo export` output shows a separate chunk loaded only on map screens, before/after sizes, and the maplibre CSS import works in Metro web. WebGL fallback "settled in the plan" is vague: on the website the spotter's only map use is "where was the cat" pin; a no-map fallback for the pin (use device location or the area list) should be named now since it changes the submit flow.

S7. R2/Cloudflare caching claim is incomplete.
- Cloudflare docs (developers.cloudflare.com/cache/concepts/default-cache-behavior): cache is by file extension; .pmtiles is not in the default list; 206 can be served from a cached whole file. So "Cloudflare's own copies at the edge serve most of them" (spec l.~130) is false unless a Cache Rule "cache everything" is added for tiles.catspotters.com. Whether a cold ranged request fills the cache is unchecked: test with curl -r and look for cf-cache-status HIT.
- CORS (docs.protomaps.com/pmtiles/cloud-storage): allow GET/HEAD, request headers Range and If-Match, expose ETag, MaxAge 3000. The spec's "allows the website's address" omits these; the pmtiles library sends If-Match, which makes browsers preflight. Origins: catspotters.com, apptest.catspotters.com, www, localhost dev and Replit preview hosts (serve-web.js shows these hosts); list them.
- The R2 free allowance wording ("10 million reads a month") is an estimate; fine since marked.

S8. Data pipeline.
- Protomaps/Planetiler copies name:en through unchanged (protomaps/basemaps OsmNames.java: `isAllowed` allowlist of name:<lang> keys, `feature.setAttrWithMinzoom(key, value)`; "name" is split by script into name/name2/name3). So an added name:en is used as-is: good. But `name:en:auto` is NOT in the allowlist and will be dropped from the tiles (spec l.~112 says "inside the file only"): record the auto flag in a side list (manifest or a CSV artifact) instead.
- Editing tags means rewriting the PBF (osmium alone cannot compute transliteration): name pyosmium/osmium-tool step and pin it; the transliteration standard: ELOT 743 gives "Agios", old signs "Ayios" (spec Risks mentions both, fine); decide Greek names that already contain Latin letters, ALL-CAPS and accented text, "Οδός" prefix kept as "Odos".
- Planetiler's Protomaps profile also downloads Natural Earth and OSM water polygons at build time (not mentioned in §1 step 3 or §7 credits): pin them, list licences (Natural Earth public domain; water polygons ODbL; Planetiler Apache-2.0; basemaps-assets fonts OFL, sprites licence unchecked). Add them to NOTICE.
- Licence implications of generated names: unchecked legal view, but the safe statement is: the generated name:en values exist only in our build, are never uploaded to OpenStreetMap (state this in the spec), and syros.pmtiles is a database derived from OSM data, so publish it under ODbL with attribution and offer the build scripts/manifest (ODbL share-alike applies to a Derivative Database; whether tiles count as a Produced Work is unchecked). §7 only says "NOTICE says the map is made by Cat Spotters from OSM (ODbL)": make it explicit that the file itself is offered under ODbL.
- "Ermoupoli with Greek underneath" is a feature of get_multiline_name when name:en exists and name is Greek (language.ts); the Protomaps English style also falls back to English in the first line; that matches what was observed.

S9. Decision B vs table: spec counts show only 1% of streets and 12% of other features have name:en, so after B, 99% of street labels and most POIs are machine spellings. Spec's "Risks" covers clumsiness only mildly; add the tourist-facing risk that machine spellings differ from road signs (and Latin place names already common on signs e.g. "Kini").

D3. "Server keeps it on disk": the old cache lived in Postgres (lib/db/src/schema/mapTiles.ts, bytea) for a reason: a Replit deployment's disk is ephemeral and multi-instance (unchecked for this deployment, but the repo's own design avoided disk). Alternative: vendor the file into the deploy bundle.

D4. Whole-file only needs more than "returns the whole file". The pmtiles JS library fetches with Range headers by default and Express sendFile/static honours Range; both would reveal which byte ranges (so which area) are being read. Fix: serve with Accept-Ranges: none and ignore Range; on the client use a custom pmtiles Source that loads the file into an ArrayBuffer once (the library supports custom sources). Cache-Control "private, max-age" for a ~10 MB response is not guaranteed to stay in the HTTP cache; consider Cache API/IndexedDB for "once per version, and the browser keeps it". Glyph/sprite requests reveal no position, fine.
